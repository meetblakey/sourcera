## 2. Headline Verdict

**§6.1–§6.6 collectively fail every authoring convention in the audit checklist except heading syntax (#11) and partial enum-registration coverage of `data_residency_region` / `MFA Enforcement Levels` (#3, partial).** The six sub-sections are v6.0.0 vintage prose that survived the v7.0.0 / v7.1.0 program windows without a §22-style or §27.4-style hardening pass. Specifically:

1. **Three independent token-scope vocabularies coexist and disagree.** §6.6.3 ships one set (`bidding:write` / `evaluation:read` / `scoring:write` / `responses:read` / `analytics:read`); Appendix J `API Token Scopes` registers a second, completely-disjoint set (`read:requirements` / `write:requirements` / … / `admin:billing`); the §32 endpoint contracts emit a third (`write:billing`, `export:kb`, `write:workspaces`, `admin:workspaces`, …). Zero values intersect across the three. A junior engineer building token scope enforcement against §6.6.3 ships a token system the §32 endpoints will reject; building against Appendix J ships a token system that does not match what §32 actually requires.

2. **Five Appendix-I error codes referenced from §6.x are not registered in Appendix I.** `plan_upgrade_required` (§6.2.2 line 9341, §33.2 line 27524), `session_expired` (§6.3.1 line 9412), `plan_limit_exceeded` (§6.6.2 line 9468 — *cited inline as "(Appendix I)"*), `token_revoked` (§6.6.4 line 9487), `token_expired` (§6.6.4 line 9489). The "(Appendix I)" inline citation at line 9468 is a false reference. A sixth, `domain_already_claimed` (§6.4.1 line 9437), is registered in Appendix I as `m6_domain_already_claimed` (line 42499), creating a four-way drift between §6.4, §48.6 (M6), Appendix I, and the §32 endpoint emitter.

3. **§6.2 MFA prose, §4.2.1 Org schema, and Appendix J `MFA Enforcement Levels` ship three different representations of the same concept.** §6.2.2 names a flag `mfa_enforcement_required` (Boolean implicit). §4.2.1 line 3562 names a field `mfa_required_org_wide` (Boolean explicit). Appendix J line 42994 registers `MFA Enforcement Levels` enum `off` / `optional` / `required`. The Appendix J enum is unconsumed; the §6.2.2 flag name does not match the §4.2.1 schema; per-Org enforcement intent ("optional" vs "required") cannot be expressed by either of the two Boolean representations.

4. **§6.2.2 / §6.2.3 / §4.2.1 contradict each other on the MFA-enforcement grace window.** §6.2.2 line 9358 says "**No grace period; enforcement takes effect immediately.**" §4.2.1 line 3562 says "members without an enrolled factor are gated out of mutation paths until enrollment completes within the §6.2.3 14-day grace window." §6.2.3 itself authors no 14-day grace window. Three-way internal contradiction.

5. **§6.2.2 references `users.mfa_enabled` (line 9340, line 9365) — the field does not exist on the §4.2.3 User entity.** §4.2.3 (lines 3594–3609) declares `id`, `email`, `first_name`, `last_name`, `avatar_url`, `timezone`, `locale`, `role_context`, `created_at`, `updated_at`, `last_login_at`, `deleted_at` only. No `mfa_enabled`. Cross-references D-1.1-003 (MfaEnrollment as an unauthored entity) but is orthogonal: the §6.2.2 prose makes a direct schema assertion that does not match §4.2.3 even after D-1.1-003 lands.

6. **§6 introduces nine surfaces — login, sign-out, MFA enrollment wizard, recovery-code display, session-expiration toast, domain-claim wizard, DNS-verification flow, guest-invite acceptance, API-token management page — and registers zero of them in Appendix M.1.** Per CI gate `appendix_m_coverage_on_diff` (§M.4) any new surface fails the gate; §6 is grandfathered against the gate but the spec is incomplete by Convention #12.

7. **§6 emits zero notification events, zero webhooks, and zero PostHog events for any of the lifecycle transitions it describes.** No `user.created`, no `user.mfa_enrolled`, no `user.mfa_unenrolled`, no `org.mfa_enforcement_changed`, no `session.created`, no `session.revoked`, no `domain.claimed`, no `domain.verified`, no `api_token.created`, no `api_token.revoked`, no `api_token.expired`, no `workspace.guest_invited`, no `workspace.guest_revoked` (the latter already filed by D-3.1-012 against §5.4). §6.7 Audit Logging (out of this prompt's scope) provides a generic `User Authentication & Sessions` audit-event family but the §6 sub-sections themselves do not bind to it.

8. **§6.3 Session Management is silent on every dimension the audit checklist requires of a session contract** — refresh semantics (sliding window vs. hard expiry), revocation-propagation latency, multi-device behavior, single-session-per-device or multi-session, mobile divergence, Convex outage handling, state-machine for the session lifecycle.

9. **§6.4 Domain Governance ships a 10-line description of a flow that §48.6 (M6 Domain Auto-Join Claim) authors as a 1,200-line sub-section** with state-machine transitions, 8 error codes, 90-day reclaim cooldown, 30-day customer-self-serve revocation, Ops M&A transfer, SIM holds, DNS retry counts, and authority attestation. §6.4 makes no reference to §48.6 and the two are silently inconsistent.

10. **§6.6 API Token Authentication describes the entity behavior across §6.6.1–§6.6.4 without a §4.2 entity definition** (D-1.1-002 captures the missing entity; this prompt files orthogonal defects on the prose).

The aggregate signal is: §6 was written before plan-tier per-console split (§34.1.3, Phase 14.9), before the M6 domain-claim sub-program (§48.6), before §22 KB MCP authentication (§22.8.3), before §32.8 billing endpoint scopes (Phase 4c), before §50.2 Ops break-glass session, and before the v7.0.0 Cross-Console Bridge (§4.7). Every later work-program left §6 behind without back-cite. The result is a spec whose authentication chapter is materially older than the rest of the corpus and contradicts it in ten distinct places.

Severity composition: 0 P0 (no regulator-blocking defects), 27 P1 (unbuildable as written), 9 P2 (ambiguous), 1 P3 (cosmetic). 37 defects total promoted to the ledger.

### 3.1 Cluster A — §6.1 Authentication Architecture (5 defects)

- **D-3.3-001 [P1 documentation_gap]** §6.1 IdP-and-flow enumeration is materially incomplete. It names SSO (SAML 2.0) + SCIM 2.0 + Email+Password as the only "authentication methods," but the spec elsewhere depends on at least four additional flows: (a) magic-link fallback (§49.1.1 line 30805 + §36.6.6 lines 36334–36346 SSO-failure path); (b) SSO via Google / Microsoft as identity sources for Seller onboarding (§4.5.10 SellerOnboardingSession line 6045 `stage_2_sso_completed_at`: "SSO (Google/Microsoft) or magic-link verification complete"); (c) API-Token Bearer flow (§6.6, §32.2) — not classified as a "method" in §6.1 despite being the dominant programmatic auth path; (d) Ops break-glass with hardware-key MFA + step-up reauth within 5 minutes (§50.2.4, evidenced via `OpsSession.auth_factor_evidence_json` at §50.4.1 line 7381). §6.1 silent on each. Missing magic-link is the worst — §49.1.1 explicitly authors it as the WorkOS-degraded fallback path; §6.1 readers cannot deduce that a magic-link path even exists from §6.1 alone.

- **D-3.3-002 [P1 documentation_gap]** §6.1 ships zero failure-mode coverage despite naming WorkOS as the authentication substrate for the entire platform. The audit prompt explicitly enumerates the failure modes: WorkOS outage, expired session, revoked org, deleted user. Spec evidence: WorkOS outage handling exists at §49.1.1 line 30805 (`workos_sso_failure_burst` synthetic alert + magic-link fallback), §36.6.6 line 36346 (2 s p95 fallback render), and §50.2.4 line 37398 (Ops break-glass during WorkOS outage — "Existing active sessions survive the outage up to their time-box; no new quorum can be collected"). §6.1 makes none of these cross-references. A junior engineer reading §6.1 alone has no signal that a WorkOS outage degrades to anything other than total auth-system unavailability.

- **D-3.3-003 [P1 surface_engine_mapping]** §6 introduces nine user-visible surfaces that have no Appendix M.1 row: (1) login screen (WorkOS-managed), (2) sign-out CTA, (3) session-expiration toast (§6.3.1 line 9412), (4) MFA enrollment wizard (§6.2.4 — "Settings → Security"), (5) recovery-code display screen (§6.2.4 line 9383), (6) domain-claim wizard (§6.4.1), (7) DNS-verification flow (§6.4.1), (8) guest-invite acceptance flow (§6.5), (9) API-token management page (§6.6 — "Settings → API Tokens"). Appendix M.1 lines 46711–47075 walked end-to-end: zero matches under "Architecture & Console Routing," zero under "Settings (§36)," zero under any cluster. CI gate `appendix_m_coverage_on_diff` per §M.4 is the runtime guard against the missing-row class but does not retroactively cover §6.

- **D-3.3-004 [P2 acceptance_criteria]** §6.1 has no numbered acceptance criteria. The §13.10 / §14.9 / §17.8 / §20.7 convention requires observable / measurable / scope-bound criteria for every feature. §6.1 is structured as bullet-list prose only. Buildability impact: a QA engineer cannot author tests for "WorkOS provides identity claims to Sourcera via OpenID Connect token upon successful authentication" (line 9320) because the assertion is descriptive, not testable.

- **D-3.3-005 [P2 glossary]** Appendix K Glossary (lines 45741+) does not define `SSO`, `SAML`, `SCIM`, `WorkOS`, `OIDC` / `OpenID Connect`, `magic link`, `Bearer token`, `WebAuthn`, `FIDO2`, `TOTP`, `recovery codes`. Each term is used across more than one section (§6, §32, §22, §31, §49, §50), triggering Convention #4 (Appendix K registration). The Phase 12.3 amendment makes Appendix K canonical; the missing entries are spec-wide hygiene gaps. Severity P2 (not P1) because the terms are industry-standard; a junior engineer can plausibly resolve their meaning.

### 3.2 Cluster B — §6.2 Multi-Factor Authentication (9 defects)

- **D-3.3-006 [P1 numerical_singleton]** §6.2.4 line 9383 inline-states "Recovery codes: 10 single-use codes generated at enrollment" — the literal `10` has no §39 row. Per Convention #10, every numerical singleton has exactly one authoritative home; §39 covers the field constraints class and §44.6 / §44.1 cover envelope / latency budgets. Recommended: add `MfaEnrollment | recovery_codes_count | 10 codes per enrollment | Hard cap; regenerate operation re-issues 10` to §39 (paired with the D-1.1-003 MfaEnrollment entity authoring).

- **D-3.3-007 [P1 data_model]** §6.2.2 lines 9340, 9365 reference "Schema field `users.mfa_enabled`" — no such field exists on the §4.2.3 User entity (lines 3594–3609 declare `id`, `email`, `first_name`, `last_name`, `avatar_url`, `timezone`, `locale`, `role_context`, `created_at`, `updated_at`, `last_login_at`, `deleted_at`, full stop). §6.2.3 line 9365 makes the reference load-bearing for the downgrade flow ("`users.mfa_enabled` remains true"). Orthogonal to D-1.1-003 (which asks for the missing MfaEnrollment entity); even after D-1.1-003 lands, §6.2.2 will still be wrong — the field belongs on `MfaEnrollment` (per-factor) or `OrgMembership` (per-membership), not on the global `User`.

- **D-3.3-008 [P1 enum]** §6.2.2 line 9354 + line 9367 references a flag `mfa_enforcement_required` on the Organization record. §4.2.1 line 3562 schema declares `mfa_required_org_wide` Boolean. The two names disagree. Appendix J line 42994 registers `MFA Enforcement Levels` enum (`off` / `optional` / `required`) — neither §6.2.2 nor §4.2.1 consumes the enum. Three concept representations for one mechanism: (a) §6.2.2 named-Boolean (`mfa_enforcement_required`), (b) §4.2.1 named-Boolean (`mfa_required_org_wide`), (c) Appendix J ternary enum. The Appendix J enum is the only representation that can express "optional" (per-user opt-in, no Org override) vs "required" (Org-wide forcing) cleanly. Also blocks Convention #3's "every Appendix J value has at least one consumer in §4–§51" — `MFA Enforcement Levels` has zero consumers as of v7.1.0.

- **D-3.3-009 [P1 consistency_drift]** §6.2.2 line 9358 declares Enterprise enforcement is **immediate** with **no grace period**: "No grace period; enforcement takes effect immediately." §4.2.1 line 3562 declares the opposite: "Setting to `true` requires every active member to have an MFA factor enrolled within the §6.2.3 grace window (14 days); members without an enrolled factor are gated out of mutation paths until enrollment completes." §6.2.3 itself (lines 9360–9374) authors no 14-day grace window — §6.2.3 covers MFA preservation across plan downgrades only. Three-way contradiction across §6.2.2, §4.2.1, and the dangling §6.2.3 reference. The §4.2.1 row is the v7.1.0 D-1V-004 remediation (per inline citation "D-1V-004 remediation, 2026-04-29"); the §6.2.2 line dates to v6.0.0 and was not updated alongside D-1V-004.

- **D-3.3-010 [P1 documentation_gap]** §6.2 specifies neither the lost-recovery-codes path nor the lost-TOTP-device path. §6.2.4 line 9383 says "10 single-use codes generated at enrollment, user must securely store" — no recourse if codes AND device are both lost. The Spec is silent on: (a) admin reset (Org Admin clears MFA factor and recovery codes for a stuck user), (b) WorkOS support escalation, (c) audit-event emission on admin reset, (d) Enterprise `mfa_required_org_wide=true` interaction (must the user re-enroll before regaining access?), (e) DSAR implication (recovery-code regeneration is a write to a "Pure-PII row" per §6.8.4 line 9642). The lost-phone-with-recovery-codes path is implicit ("user enters a recovery code") but the lost-phone-without-recovery-codes path is unauthored.

- **D-3.3-011 [P1 state_machine]** §6.2 has no MFA enrollment state machine. The lifecycle is implicit: `none` → `pending_enrollment` (Enterprise enforcement engaged but not yet enrolled) → `enrolled` (TOTP or WebAuthn factor present) → `enrolled_with_recovery_codes_unused` → `enrolled_with_recovery_codes_partially_consumed` → `disabled` (admin reset) → `re-enrolling`. Per Convention #5, this is a state-machine table (`From` / `To` / `Trigger` / `Conditions` / `Notes`), not prose. Authoring this state machine is a precondition for D-1.1-003 (MfaEnrollment entity) and D-3.3-014 (acceptance criteria).

- **D-3.3-012 [P1 webhook]** §6.2 emits zero notification, webhook, or audit events. The MFA lifecycle has at minimum five customer-relevant transitions: `mfa.enrolled`, `mfa.unenrolled`, `mfa.recovery_codes_regenerated`, `org.mfa_enforcement_required_set`, `org.mfa_enforcement_required_cleared`. None registered in Appendix C (Notification Event Catalog) or Appendix G (PostHog Taxonomy). §31.1 / §31.2 conventions on HMAC-SHA256 / `event_id` idempotency / DLQ at 5 failures apply; the events are unauthored.

- **D-3.3-013 [P2 retention]** §6.2 silent on retention of MFA enrollment records and recovery codes. §6.8.4 line 9642 lists "MFA factors, recovery codes" in the "Pure-PII rows ... Hard-delete; no tombstone" class but the per-entity retention rule is missing. Recovery-code regeneration semantics (do prior 10 codes invalidate?) and TOTP-secret rotation semantics (is the WorkOS-side secret rotated when an Org changes the `mfa_required_org_wide` flag?) are also silent. Convention #9.

- **D-3.3-014 [P2 acceptance_criteria]** §6.2 has no numbered acceptance criteria. The §13.10 / §14.9 / §17.8 / §20.7 convention applies — the §6.2.1 plan-tier matrix and §6.2.3 transitions are testable behaviors that must be expressed as numbered ACs. Buildability: a QA engineer cannot author tests for "If enforcement is enabled, all users without MFA receive in-app notification: 'Your organization requires multi-factor authentication. Enroll now.'" without explicit observable inputs / outputs / thresholds.

### 3.3 Cluster C — §6.3 Session Management (7 defects)

- **D-3.3-015 [P1 numerical_singleton]** §6.3.1 inline-states four numerical singletons: `Session Duration` 24h fixed (Free/Starter/Growth/Scale), 24h default + 12–72h configurable (Enterprise); `Idle Timeout` 2h fixed, 2h default + 30min–4h configurable. None are registered in §39 (Object Size Constraints) or §44.1 (Performance Targets) or §34.1 (Plan Tier Definitions) — the three canonical homes for plan-gated numerical singletons. Convention #10 violation; CI gate equivalent to `solo_tier_numeric_single_source` cannot be authored against §6.3.1 because the values have no canonical home to single-source against.

- **D-3.3-016 [P1 documentation_gap]** §6.3 silent on session refresh semantics. The 24h `Session Duration` is named but the spec does not declare whether it is (a) an absolute timeout from `created_at` (hard expiry — the user is logged out at 24h regardless of activity), (b) a sliding window from `last_activity_at` (the session refreshes on each request and only expires after 2h of idle PLUS 24h hard cap), or (c) a sliding window with no hard cap. The audit prompt explicitly calls out "refresh semantics" as a required spec element. WorkOS-side session refresh behavior is a contract that varies by configuration; §6.3 must declare which configuration Sourcera adopts.

- **D-3.3-017 [P1 documentation_gap]** §6.3 silent on revocation-propagation latency. Three revocation paths are implied by the spec: (a) user clicks Sign Out (§6.3.1 line 9418); (b) Org Admin revokes a user's membership (§4.2.2 `deleted_at` populated, §5.x deactivation); (c) Org Admin enables `mfa_required_org_wide` and the user is force-re-authenticated (§4.2.1 line 3562). For each, the latency from revocation-write to "no further requests succeed under that session" is unspecified. The audit prompt explicitly requires "revocation propagation latency" as a session-contract element.

- **D-3.3-018 [P1 state_machine]** §6.3 has no session state machine. The lifecycle is implicit: `created` → `active` → `idle` (no API request, WebSocket activity, or UI interaction within 2h) → `expired` → `terminated_by_logout` / `terminated_by_admin_revoke` / `terminated_by_org_revoke` / `terminated_by_user_delete`. Per Convention #5. The §6.3 inline prose at lines 9410–9414 ("Session Expiration Behavior") is a sequence of bullets, not a state-machine table.

- **D-3.3-019 [P1 documentation_gap]** §6.3 silent on Convex outage handling. §1.5 (line 1339) names Convex as the unified database; §22 KB MCP and §4.3.14 Presence Records depend on Convex Subscription / Reactivity Layer (§7.5, §1.5 Convex layer). A Convex outage during an active session: does the session degrade gracefully (HTTP 503 with `Retry-After`), or does the user observe a hard sign-out? §29.11 Full-Screen Incident Surface authors a critical-incident takeover but the session-side fallback is unauthored. The audit prompt explicitly calls out Convex outage as a required edge case for §6.3.

- **D-3.3-020 [P1 documentation_gap]** §6.3 silent on mobile session semantics. §38.4 / §38.8 (Mobile Feature Parity) authors a separate mobile-vs-desktop matrix; §6.3 makes zero mobile cross-references. Open questions: (a) does the mobile app share a session with the web app (single-session-per-WorkOS-identity) or hold a separate session (multi-session); (b) does the mobile app honor the 2h idle timeout (mobile typically uses biometric re-unlock instead); (c) does Sign Out from desktop kill the mobile session via the SharedWorker / localStorage path described at line 9421 (the SharedWorker / localStorage path is a desktop-only mechanism); (d) does push-notification arrival count as "activity" for the idle-timeout calculation. CLAUDE.md §12 Edge-Case Discipline requires mobile divergence coverage on every applicable feature.

- **D-3.3-021 [P2 documentation_gap]** §6.3.1 line 9421 declares the cross-tab sign-out implementation — "All tabs/windows are signed out immediately (via SharedWorker or localStorage events)." This is an implementation detail, not a behavior contract. The behavioral assertion (cross-tab sign-out is immediate and reliable) is the right spec; the implementation choice (`SharedWorker` *vs* `localStorage` events) is engineering. The mixed alternation is also lossy — `SharedWorker` is a strict superset of capability vs. `localStorage` events; an honest spec declares "use SharedWorker; fall back to BroadcastChannel; fall back to `localStorage` events on environments that lack both" or simply asserts the contract and lets engineering choose.

### 3.4 Cluster D — §6.4 Domain Governance (7 defects)

- **D-3.3-022 [P1 error_code]** §6.4.1 line 9437 emits error code `domain_already_claimed` on the multi-Org race. Appendix I line 42499 registers `m6_domain_already_claimed` (HTTP 409). The §48.6 / M6 sub-section (lines 33710 / 33817 / 33823) emits the `m6_*` form. §6.4 ships a non-`m6_`-prefixed code that is not in Appendix I. Either §6.4 must be aligned to `m6_domain_already_claimed` (recommended — §48.6 is the authoritative domain-governance home), or Appendix I must add a separate `domain_already_claimed` row (rejected — duplicates the `m6_` code's semantics).

- **D-3.3-023 [P1 consistency_drift]** §6.4 ships a 10-line domain-governance description that contradicts §48.6's 1,200-line authoritative authoring. §6.4 says: "Verification succeeds: domain is marked `verified` and linked to Organization." §48.6 / Appendix I authors eight error codes covering: `m6_domain_already_claimed` (UNIQUE collision), `m6_domain_shared_use_rejected` (shared-use domain — gmail.com etc.), `m6_claim_sim_hold_active` (Signal Integrity Monitor hold), `m6_claim_reclaim_cooldown_active` (90-day same-Org cooldown after revocation), `m6_domain_verification_pending` (verification not yet complete), `m6_domain_verification_failed` (DNS TXT not found after N retries), `m6_claim_revocable_window_expired` (outside 30-day customer-self-serve revocation window), `m6_ops_transfer_evidence_required` (M&A transfer evidence). §6.4 covers only `m6_domain_already_claimed` (under the wrong name per D-3.3-022). The other seven flows are authoritative in §48.6 but invisible to a §6.4-only reader. §6.4 must either (a) become a thin pointer to §48.6 or (b) absorb the §48.6 detail. Recommended (a).

- **D-3.3-024 [P1 state_machine]** §6.4 has no state machine. Domain lifecycle is at minimum: `unclaimed` → `pending_dns_verification` → `verified` → `suspended_dns_dropped` (post-verification DNS removal — D-3.3-025) → `released_by_admin` / `released_by_ops_transfer` / `revoked_by_sim` → `cooldown_active` (90-day) → `unclaimed`. §48.6 authors related state but the §6.4 view is missing.

- **D-3.3-025 [P1 documentation_gap]** §6.4 silent on three operational behaviors. (a) DNS-verification retry count and back-off: §48.6 cites "DNS TXT not found after N retries" but neither §6.4 nor §48.6 specifies N (the literal value). (b) Periodic re-verification: §6.4 line 9438 says "Domain verification persists across plan changes" but is silent on whether the system periodically re-validates the DNS TXT record post-verification. If yes, what cadence? If no, what happens when an admin removes the DNS record after verification — does the claim survive indefinitely? (c) The implicit answer to (b) appears to be "no re-verification" given the wording, but a hostile reviewer would expect the spec to say this explicitly because it has security implications (a former Org Admin who removes the DNS record cannot revoke the claim).

- **D-3.3-026 [P1 acceptance_criteria]** §6.4 has no numbered acceptance criteria. The §13.10 / §14.9 / §17.8 / §20.7 convention applies. §6.4.1 Edge Cases (lines 9436–9440) is bulleted prose, not testable ACs.

- **D-3.3-027 [P2 documentation_gap]** §6.4 silent on subdomain handling. Open questions: (a) can Org A claim `acme.com` and Org B claim `eu.acme.com` simultaneously (subdomain split)? (b) If Org A claims `acme.com`, are subdomains (`engineering.acme.com`) auto-included or must each be separately claimed? (c) Email-domain match for invitation auto-routing — is `@eu.acme.com` matched against an `acme.com` claim or only against a separate `eu.acme.com` claim? §48.6 covers this in `m6_domain_shared_use_rejected` partly but the subdomain-vs-shared-use distinction is unauthored. Mid-market enterprises commonly hold `@subsidiary.acme.com` mailboxes; the silence is a real-world build blocker.

- **D-3.3-028 [P1 plan_gating]** §6.4 declares "Enterprise Organizations only" (line 9425) without §5.11 / §34.1.1 / §34.1.2 / §39 row reference. Convention #8 requires plan-gated capabilities to cite the source table inline, never duplicate the plan name. §34.1.1 cell **Custom Domain (Auto-Join)** would be the natural home; §5.11 row "Manage custom domain" would be the role-keyed home. Neither exists. The Phase 14.9.1 inline-tier-list backlog (per CLAUDE.md §16) covers this class but §6.4 is not on the 27-location list.

### 3.5 Cluster E — §6.5 Guest Users & SSO Bypass (3 defects)

- **D-3.3-029 [P1 firewall_leakage]** §6.5 silent on cross-Org guest identity reuse. §4.2.3 User is keyed by `email` (unique). A user `blake@acme.com` invited as a guest to Org A can also be a regular SSO user at Org B (own employer). When the user authenticates via WorkOS email+password (the §6.5 path) for Org A, what governs the active-Org context for subsequent requests? Is it (a) the user picks active Org at the WorkOS post-auth callback; (b) the magic-link / invite token carries the Org binding; (c) the `X-Sourcera-Active-Org` header is required. §1.4 cross-references hint at active-Org scoping but §6.5 makes no mapping. Counterfactual: a guest whose primary email is also their employer's SSO-managed identity would, in the absence of an active-Org rule, transparently bypass their own Org's SSO when they auth via the §6.5 email+password path. This is an SSO-bypass vector and a P1 firewall_leakage defect.

- **D-3.3-030 [P1 documentation_gap]** §6.5 line 9447 says "Guest user signs in via email+password, MFA optional if plan supports it." §6.2.1 plan-tier matrix declares Free-tier MFA "Not available." A guest at a Free-tier Org therefore cannot enroll in MFA. A guest at an Enterprise Org with `mfa_required_org_wide=true` (§4.2.1) — must the guest enroll? §6.2.2 line 9357 says "Users without MFA are prompted to enroll on next login; cannot access Sourcera until enrolled" — does this apply to guests? Guests are explicitly exempt from SSO via §6.5; the spec is silent on whether they are also exempt from `mfa_required_org_wide`. For most enterprises this matters: a buyer-Org Enterprise customer with strict MFA enforcement invites a vendor representative as a guest — does the guest need to enroll in MFA in the buyer's Org? Recommended: §6.5 must declare guest interaction with Org-wide MFA enforcement explicitly.

- **D-3.3-031 [P2 documentation_gap]** §6.5 makes no cross-reference to §5.4 Guest Role & Permission Profiles or to D-3.1-009 / D-3.1-010 / D-3.1-011 / D-3.1-012 (the Phase 3.1 Guest defect family covering scope isolation across modern surfaces, lifecycle states, profile changes, and revocation). §6.5 covers the auth path and §5.4 covers the authz scoping; the two are silently coupled with no lateral pointer. A junior engineer reading §6.5 alone cannot determine which permission profile a freshly-invited guest gets by default (§5.4.1 read_only? §5.4.4 full_participant?), how the auth flow interacts with the §5.4.6 lifecycle states (proposed in D-3.1-010), or whether the §6.5 guest revocation flow at line 9450 ("Guest access may be revoked by Organization Admin, triggering account deactivation") is the same flow as §5.4.8 (proposed in D-3.1-012).

### 3.6 Cluster F — §6.6 API Token Authentication (12 defects)

- **D-3.3-032 [P1 enum]** Three independent token-scope vocabularies coexist and disagree. (a) §6.6.3 lines 9474–9479 ships `bidding:write`, `evaluation:read`, `scoring:write`, `responses:read`, `analytics:read` — five scopes in noun:verb form. (b) Appendix J line 42998–43000 registers `API Token Scopes` as `read:requirements`, `write:requirements`, `read:responses`, `write:responses`, `read:scores`, `write:scores`, `read:workspaces`, `admin:integrations`, `read:billing`, `write:billing`, `admin:billing` — eleven scopes in verb:noun form. (c) §32 endpoint contracts emit additional scopes that appear in neither §6.6.3 nor Appendix J: `write:workspaces` (line 19053 vendor-disqualification endpoint), `admin:workspaces`, `export:billing`, `export:kb` (lines 27323, 27423 — KB export endpoint, with explicit Phase-12 / §22.18 P1 invariant that `export:kb` is plan-tier-invariant). Zero values intersect across (a) ↔ (b); two values (`read:billing`, `write:billing`) appear in (b) ↔ (c); zero in (a) ↔ (c). The `scope_insufficient` error code at Appendix I line 42334 / KB-export `kb_export_token_scope_insufficient` line 42399 cannot be deterministically emitted because the §32 endpoint declares a scope name that the §6.6.3 vocabulary does not cover. P1 by Audit Severity rule "missing field-level schema, missing acceptance criteria, missing state machine, missing error code, missing webhook contract, missing plan-gating row in §5.11/§34.1/§39, missing retention/DSAR/residency clause, conflicting numerical singleton." Recommended resolution: Phase 12.1-style canonicalization. Adopt the verb:noun form (matches the §32 endpoint contracts, which are the consumers); retire the §6.6.3 vocabulary; re-register Appendix J with the union of (b) and (c) plus per-scope semantics; author scope-enforcement validator `appendix_j_api_token_scope_endpoint_consistency` per §M.5 catalog pattern.

- **D-3.3-033 [P1 numerical_singleton]** §6.6.1 line 9458 inline-states the token format `srck_[org_id_prefix]_[32_character_random_alphanumeric]`. The literal `32` (random-alphanumeric length) has no §39 row and no Appendix J registration. The format string itself is an inline numerical / structural singleton consumed by §32.2 token-validator code. §39 is the authoritative home; §6.6.1 must cite the §39 row. Recommended row: `ApiToken | secret_random_segment | 32 chars (alphanumeric, base62 or [a-zA-Z0-9])`. Also: the `[org_id_prefix]` length is unspecified — at line 9459 the example shows `srck_acm_…` (3-char `acm`) but the spec does not declare whether the prefix is fixed-length, derived from the slug, or arbitrary.

- **D-3.3-034 [P1 plan_gating]** §6.6.4 line 9488 says "Token may include optional expiration date (default: no expiration)." Default-infinite tokens for a programmatic-access surface is a security posture choice that should be plan-gated, not a default. §5.11 / §34.1 has no row for "Default token expiration" or "Maximum token lifetime by plan." Enterprise security teams typically require per-plan-tier expiration policies (e.g., Enterprise: 90-day forced rotation; Scale: 180-day; Growth and below: no policy but max 1y); the spec has none. Cross-reference: F-169 inventory row claims "Enterprise enforced 90-day rotation" but §6.6.4 does not author this. P1 by Severity rule "missing plan-gating row in §5.11/§34.1/§39."

- **D-3.3-035 [P1 firewall_leakage]** §6.6.3 line 9473 says "Tokens are scoped to the Organization that created them; cannot access other Organizations." Silent on **console** firewall. A token created by a Buyer-side Workspace Owner in a dual-console Org (`console_modes_active = both` per §4.2.1) — can it call seller-side endpoints (§32.x seller-scope endpoints)? Per §1.3 console firewall doctrine, console-scoped data isolation must be enforced at every layer including API tokens. The §32 endpoints emit `console_isolation_violation` (Appendix I line 42240) but §6.6 makes no statement about how tokens carry console scope. Counterfactual: a buyer-side Org Owner who creates a token with the §6.6.3 scope `bidding:write` (or any scope name from any of the three vocabularies in D-3.3-032) — is the token usable against seller-side `bid_workspace_*` endpoints? The audit cannot determine intent without a spec answer. Recommended: §6.6.3 must declare a `console_scope ∈ {buyer, seller, both}` axis on tokens, set at creation time and immutable; tokens with `console_scope=buyer` return HTTP 403 `console_isolation_violation` on seller endpoints and vice versa.

- **D-3.3-036 [P2 documentation_gap]** §6.6.4 token rotation flow not authored. The §32 endpoint contracts that consume tokens depend on rotation as a first-class flow (Enterprise security posture, periodic credential refresh, suspected-compromise response). §6.6.4 documents creation and revocation; rotation is implicit ("revoke + create a new one"). Open questions: (a) is there a single-step rotation endpoint (`POST /v1/api-tokens/{id}/rotate`) that returns a new secret without breaking in-flight requests? (b) does rotation preserve the token's scope and last_used_at? (c) is rotation audit-logged with both the old and new token IDs?

- **D-3.3-037 [P2 documentation_gap]** §6.6 silent on per-token rate-limit allocation. §32.4 declares rate-limit classes; whether each token shares the Org's rate-limit class or carries its own per-token allocation is unspecified. Counterfactual: an Org with five tokens running a parallel-batch ingestion — does the rate-limit class apply to the union (one shared bucket) or per-token (five buckets)? Production-tuning decision; spec must declare.

(Token webhook events, token retention rules, and token DSAR coverage are forwarded to Phase 8 (API + Webhook) and Phase 6 (Privacy & Residency) per §5 below; not separately filed in this prompt's scope.)
