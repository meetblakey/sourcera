## §2 Dependency DAG & Execution Order {#walk-2-dag}

Classes are ordered so that every program's prerequisites are landed before it runs. Authoring an API that cites an unregistered enum, or a field table that cites a not-yet-authored entity, violates Conventions #3/#1 and forces rework. The DAG eliminates that.

```
TIER 0 — CATALOG ROOTS (referenced by everything downstream)
  P1  enum ............... Appendix J        (no deps)
        │
TIER 1 — ENTITIES
  P2  data_model ........ §4                 (cites enums)
        │
        ├───────────────┬───────────────┬──────────────┐
TIER 2 — ENTITY-DERIVED CONTRACTS
  P3  state_machine      P4 error_code      P8 retention   P10 residency
   (App L; cites P2)      (App I; cites P2)   (§40.2; P2)    (§1.6/§40/§42; P2)
        │                    │                   │
        └──────┬─────────────┘                   │
TIER 3 — INTERFACE CONTRACTS                      │
  P5  api (§32; cites P2,P3,P4)                    │
  P6  webhook (§31, App C/G; cites P2,P4)          │
        │                                          │
  P7  notification (App C; cites P6)               │
                                                   │
TIER 4 — PRIVACY/SECURITY (cites entities + interfaces + retention)
  P9  dsar (§6.8.4; cites P2,P8)  ←────────────────┘
  P11 firewall_leakage (§4.7; cites P2,P5,P6)
        │
TIER 5 — ACCESS & COMMERCIAL GATING
  P12 rbac (§5.11)
  P13 plan_gating (§5.11/§34.1/§39; cites P12)
  P14 entitlement (§34.8.5/§21.4; cites P13)
  P15 numerical_singleton (cites §34/§39 tables stabilized by P13/P14)
        │
TIER 6 — SURFACES & UX CONTRACTS
  P16 surface_engine_mapping (App M.1)
  P17 acceptance_criteria (§13.10-style; cites stabilized features)
        │
TIER 7 — INSTRUMENTATION & OPS
  P18 instrumentation_gap (App G + Datadog + AuditEvent triad)
  P19 posthog_event (App G; cites P18)
  P20 observability (§42; cites P18)
  P21 performance_budget (§44)
  P22 growth_mechanic_gap (§48; binds AE-V11-01)
        │
TIER 8 — META / CLEANUP (run last; depend on all upstream edits)
  P23 documentation_gap (narrative completion)
  P24 ci_gate (§M.5 promotion of gates introduced by P1–P23)
  P25 consistency_drift (terminology/anchor/numeric/appendix normalization)
        │
  CLOSE-OUT — verification + reconciliation rollup + stamp-gate readiness
```

**Why this order.** (1) `enum` first because field tables, state machines, API/webhook schemas, and notification matrices all cite Appendix J — registering enums up front lets every downstream program cite rather than stub (Convention #3). (2) `data_model` second because retention, DSAR, residency, API, webhook, firewall all reference entity fields. (3) `numerical_singleton` after `plan_gating`/`entitlement` because the scrub replaces inline literals with citations to §34/§39 tables — those tables must be stable first. (4) `ci_gate` and `consistency_drift` last because they normalize and promote artifacts introduced by the preceding 23 programs; running them earlier guarantees re-runs.

## §3 Per-Pass Execution Contract {#walk-3-contract}

Every program executes the identical seven-step atomic cadence. No step is skippable.

1. **Re-derive true-open set.** Intersect canonical `status=open` ∧ `class=<class>` MINUS supplementary `→remediated`/`→superseded` (D-CONS-001 guard). Output: the pass work list with line anchors.
2. **Read affected sections end-to-end.** For each defect, read the cited Master Spec section/appendix in full (not by grep) before authoring. Read the relevant existing appendix entries to match format exactly.
3. **Author at Master Spec fidelity.** Apply the class authoring shape (§4 below). Register every new enum (App J), term (App K), state machine (App L), error code (App I), webhook (App C + App G), surface (App M.1). Cite numerical singletons to their canonical home (§34/§39/§44/§6.8/§40.2/§42.1) — never inline.
4. **Ledger transition (canonical-row).** Transition each closed defect's canonical `status` cell `open → remediated` (or `partially_remediated`/`superseded`) and append the landing-site citation to `links`. **Per D-CONS-001, the closure MUST land on the canonical row, not only a supplementary table.**
5. **Reconciliation block.** Append to `RECONCILIATION.md → v7.2.0-REM Program → Phase 12 — <class>`: edit summary, defect-id → landing-site map, AE-row → status map, CI-gate → §M.5-row map, conflicts resolved, sign-off scoreboard.
6. **Self-challenge pass (Convention #15).** Re-read authored output as a hostile staff engineer over 5 random closed defects: would code review pass it? would QA accept the ACs? could a junior build unambiguously? Revise in place; log findings in the phase verify doc.
7. **Counterfactual pass (Convention #16).** For each authored section enumerate ≥3 realistic failure modes (partial failure, adversarial input, dependency outage); confirm handling exists or author it before saving.

**Authored Extensions.** Where a source is underspecified and detail is authored, mark `Authored Extension — requires human sign-off` and append a row to `_integration/AUTHORED_EXTENSIONS_LEDGER.md → v7.2.0-REM Program` with `pending` status. AE rows ratify before the v7.2.0 stamp per the ledger's release-gate policy. Sole-signer posture per **AE-V72REM-00** holds until named-role hires; differentiated sign-offs (Security / Privacy Officer / KB Lead) recorded inline where the class requires them (firewall_leakage → Security; dsar/residency → Privacy Officer; growth_mechanic_gap → Analytics+Product).

**Backup discipline (Convention #14).** One backup per *session* (not per defect) before the first destructive edit of that session: copy `Sourcera_Master_Spec.md` → `legacy-import:_versions/Sourcera_Master_Spec.v7.1.0a-pre-v72REM-Phase12-<class>-<YYYY-MM-DD>.md`; record byte size + md5 in `RECONCILIATION.md`.

**Batching.** XL programs (data_model, acceptance_criteria, plan_gating) split into section-family batches of ≤25 defects per batch; each batch is a complete cadence 1–7. L/M/S programs run as a single pass unless the true-open set exceeds 25.

## §5 Exit Criteria & Stamp-Gate {#walk-5-exit}

The walk is complete for v7.2.0-stamp purposes when:

1. Every §3.2 program's true-open set is `remediated`/`partially_remediated`/`superseded` on its **canonical** ledger row (D-CONS-001 satisfied for the class).
2. Every authored enum/term/state-machine/error-code/webhook/surface is registered in its appendix (J/K/L/I/C+G/M.1).
3. Every new CI gate is catalogued in §M.5 with a Runtime-status assignment (runtime_active or spec_binding_pending_pack_<id>).
4. Every AE row authored during the walk is `pending`→ratified (or carries a v7.1.2/v7.2.1 re-target with rationale) before stamp.
5. Counterfactual + self-challenge logs exist for all 25 programs in `_audit/PHASE_V72REM_PHASE_12_<class>_VERIFY.md`.
6. Reconciliation rollup reconciles defect-closure counts vs ledger transitions with zero unaccounted deltas.

## §7 Course Correction — D-CONS-001 Reconciliation-First (added 2026-06-15) {#walk-7-correction}

**Trigger.** Program 1 (enum) Batch 1 attempted to register 7 `D-AJ` enums whose canonical rows read `open`; verification found all 7 already registered in the Master Spec "Phase 2V Audit-Remediation Enum Registrations" section (2026-05-03). The canonical rows were lagging (D-CONS-001), not open. Batch 1 was reverted (0 net spec delta); the 7 rows were propagated to `remediated 2026-05-03`. Full record: `RECONCILIATION.md → v7.2.0-REM Phase 12 enum`; `_audit/PHASE_V72REM_PHASE_12_enum_VERIFY.md`.

**Root cause.** Two compounding traps: (1) source defects cite **stale line numbers** (pre-Phase-9/10 spec was ~46K lines; now 53.7K), so location-based checks miss moved content; (2) the canonical ledger `status` cell lags the spec body by **≥390 rows** (D-CONS-001) — `status=open` is not evidence a defect is truly open.

**Binding amendments to §3 step 1 (true-open derivation).** Before authoring any registration/section in any program:
1. Grep the spec body for the artifact in **all heading/format variants**: `#### \`name\``, `### \`name\``, `**\`name\`**`, `**\`name\` enum`, and table-row forms.
2. Grep the `DEFECT_LEDGER.md` **supplementary status-transition tables** (L639–870, 1745–1804, 2435–2562, 2757–2820, 3094–3135, 3428–3460, 3700–3780, 4826–4990, 5264–5290, 5813–5860) for an existing `<id> … → remediated/superseded` row.
3. Only if BOTH return nothing is the defect truly open and eligible for authoring. Otherwise it is a **D-CONS-001 canonical-lag propagation** (update the canonical `status` cell + `links`; do NOT re-author).

**Recommended re-sequencing (operator decision).** Run a **D-CONS-001 reconciliation/triage pass per program FIRST**, splitting each program's canonical `open` set into (a) already-closed-in-body → propagate, and (b) genuinely-missing → author. Only (b) feeds the authoring cadence. This (i) prevents repeating the Batch-1 duplicate error across the other 24 programs, (ii) likely shrinks the true authoring surface far below the headline ~762, and (iii) advances the already-staged v7.1.1 D-CONS-001 ledger-hygiene pass as a by-product. The triage is read-mostly and low-risk; authoring is deferred until the residual is known.
