## 2. How to Use This Program

1. **One Cowork session per prompt.** Run each prompt below as a single Cowork session. Do not interleave prompts within a session — each prompt has a binding inputs / outputs / verification contract that requires a clean Opus context.
2. **Run in numeric order within a phase.** Phases have ordering dependencies — P0 spec edits before AE ratification; AE ratification before P1 cluster execution; P1 catalog completeness before runtime wiring.
3. **Adversarial verification before phase advance.** Every phase's verification prompt (`Prompt VN`) must pass before the next phase begins. Halt rule: any open P0 in the phase's scope → halt the program; remediate before advancing.
4. **AE Ledger is the gating artifact for ratification phases.** Phases 7, 8, 9 each work against a defined AE-Ledger cluster set in `_integration/AUTHORED_EXTENSIONS_LEDGER.md`. Phase advance requires every targeted row to transition `pending` → `approved` / `acknowledged` / `superseded`.
5. **Backups before destructive edits.** Each Master-Spec-editing phase backs up the current Master Spec to `_versions/Sourcera_Master_Spec.v7.1.0-pre-<phase-id>-<YYYY-MM-DD>.md` before the first edit lands. Backup md5 hashes are recorded in `_integration/RECONCILIATION.md → v7.2.0-REM Program` block.
6. **Reconciliation log is append-only.** `_integration/RECONCILIATION.md → v7.2.0-REM Program` block records every phase decision, conflict resolution, and AE ratification. Do not delete entries; transition `status` instead.
7. **Stamp gates.** Four stamps land during this program: v7.1.0a (Phase 6 close), v7.1.1 (Phase 19 close), v7.1.2 (Phase 14 close, if Phase 11.5 backfill is decoupled per `AE_RATIFICATION_RECOMMENDATIONS.md §4` option b), v7.2.0 (Phase 20 close). Each stamp follows the Phase 14.20-pattern protocol: backup, version bump, changelog summary, terminator resolution, CLAUDE.md update, reconciliation log entry, sign-off scoreboard.

## 3. Global Verification Protocol

Every phase ends with a verification prompt that exercises three checks before sign-off:

1. **STRUCTURAL.** Every targeted defect-id has a Master Spec edit landing site cited in the reconciliation log; every targeted AE row has a ledger-status transition; every targeted CI gate has a §M.5 catalog row update and an implementation-pack assignment.
2. **ADVERSARIAL.** A 5-sample spot-check of the phase's defect closures against the current Master Spec text. Sample selection is random within the phase's scope. Reproducibility of evidence cited in `_audit/DEFECT_LEDGER.md` is the pass criterion.
3. **SIGN-OFF.** Zero open P0 in the phase's scope; zero open P1 where the phase's stated success criteria require closure; named-owner sign-off recorded in the reconciliation log.

Halt rules:

- Any P0 in the phase's scope → halt; remediate before advancing.
- Adversarial spot-check fails on ≥ 2 of 5 samples → halt; re-walk the phase before sign-off.
- AE ratification phase: any unprocessed `pending` row in the cluster → halt; do not advance.
- CI gate phase: any §M.5 row missing the per-row runtime-status assignment → halt.
